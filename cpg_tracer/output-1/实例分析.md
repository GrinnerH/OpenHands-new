# njs.cve-2021-46462

Sanitizer 报告 — 崩溃位置与堆栈回溯

提供的 AddressSanitizer 报告表明，程序在 njs_object_set_prototype 函数中发生崩溃，崩溃位置为 njs_object.c 文件的第 2136 行第 24 列。报告指出发生了段错误（SEGV），这是由于读取了一个无效的内存地址。堆栈信息表明，该函数由 njs_object_prototype_proto 调用（位于第 2162 行），最终是由 JavaScript 属性赋值 __proto__ 所触发。关键调用帧包括：

帧 0： njs_object_set_prototype（崩溃点）— /src/njs_object.c:2136:24

帧 1： njs_object_prototype_proto — /src/njs_object.c:2162:19

帧 2： njs_value_property_set — /src/njs_value.c:1215:19

总结行明确指出崩溃源：“AddressSanitizer: SEGV […] in njs_object_set_prototype”。这表明在访问结构体字段 proto->__proto__ 时，proto 是一个空指针或非法对象，从而导致段错误。

PoC 触发路径

GitHub 上给出的 JavaScript PoC 利用了 Function.prototype.apply 与数组原型操作组合来触发该崩溃：

function main() {
    const v3 = [23490, 23490, 23490, 23490];
    const v4 = {};
    v3.length = 1577595327;
    const v9 = Object.apply(...v4, v3);
    v3.__proto__ = v9;
}
main();


其作用机制如下：

v3 是一个包含四个整数的数组。随后它的 .length 被手动设为一个巨大的值（1577595327），制造一个极长但大部分未初始化的数组。

v4 是一个空对象。

Object.apply(...v4, v3)：尝试使用 Object 构造器调用 .apply 方法，传入 v4 和 v3。由于 v4 并非可迭代对象，但在 NJS 中可能被解释为 Object(v4, v3) 或等价形式，即尝试以 v3 的内容作为参数调用构造函数。

返回值 v9 被赋予 v3.__proto__，即将数组 v3 的原型替换为返回的对象 v9。

关键在于这个 v9 值可能是一个不符合预期结构的对象。当传入 njs_object_set_prototype 之后，代码试图执行 proto = proto->__proto__，但 proto 指向的是非法或空内存，从而引发段错误。

补丁分析（修复点与修改逻辑）

该漏洞在 NJS 0.7.2 版本中被修复。补丁位于 src/njs_function.c 文件中的 njs_function_prototype_apply 函数（约第 1385 行）。

修改前： 原有逻辑对第二个参数 arr_like 进行判断，如果是数组，则直接取其 arr->start 和 arr->length 启动调用逻辑。该逻辑会在 length 极大时触发不合理的数据展开。

修改后： 删除了数组的快速路径，新增了更严格的类型检查：

if (!njs_is_object(arr_like)) {
    njs_type_error("second argument is not an array-like object");
    return NJS_ERROR;
}


修复效果： 要求 apply 的第二参数必须为真正的对象，杜绝了构造异常对象的路径，从源头防止 v9 这类非法对象流入 njs_object_set_prototype。

## 4. 这次实例对我们模板的启发（后面要补的）

这个 case 很典型地暴露出 **“VM 操作数/栈槽变量” 的短板** —— 也就是你自己担心的：

> 当 sanitizer 报告只给出一条复杂表达式（`next->array->length`），
> 又看不出明确的 CWE，
> 而真正的源头是通过 VM 宏/操作数表间接传进来的时候，
> 目前的模式库还不够。

具体来说，后续需要补的东西大概有三类：

1. **名称驱动的 fallback 查询**（在 `.ddgIn` 失败时触发）
   - 针对 `value2` 这种局部变量，增加模板，比如：
     ```scala
     // 所有对 value2 的赋值
     cpg.method.nameExact("njs_vmcode_interpreter")
       .assignment
       .where(_.target.codeExact("value2"))
       .map(a => (a.lineNumber, a.code)).l

       .call
       .argument.codeExact("value2")

     ```
   - 这可以绕过 DDG 的“断链”，至少先把「所有写 value2 的点」列出来。

2. **专门的 VM 操作数 / bytecode 模式**
   - 例如：识别出类似 `njs_vmcode_operand(vm, ... &value2)`、`frame->values[...]` 这类宏/数组访问，把「槽号/索引」当成新的 BOUNDS_INDEX 源，

   - 这一块在 prompts 里目前完全没有 pattern，只能靠 LLM 自己“猜”，所以它自然就停了。

3. **S4 兜底式 reachableByFlows**
   - 目前这一 run 里没有任何 `expect_paths=true` 的查询，说明 LLM 从头到尾都没认为“已经有足够的源集合可以跑 `.reachableByFlows`”；
   - 可以在模板里规定：
     - 一旦拿到了一个**局部链条**（比如 `value2->data.u.next` → `next` → `next->array->length`），

# njs.cve-2022-38890
这个数据流分析的轨迹在初期是正确的，但在关键节点上出现了偏差，导致它走向了错误的方向。

分析师（Joern 助手）最终找到了一个“ bug”，但它很可能不是导致此 CVE 的真正根源。

1. 正确的起点 (迭代 1-4)
分析的开始是正确的：

Sink (SINK)： njs_utf8_next (位于 njs_utf8.h:54)。

Caller (调用者)： njs_string_offset (位于 njs_string.c:2545)。

Focus (焦点)： njs_utf8_next(start, end)。分析正确地将 FOCUS 锁定在传递给 p 指针的 start 变量上。

2. 关键的错误转向 (迭代 5)
这是分析出错的地方：

分析师的结论： 在迭代 5 中，分析师查看了迭代 4 的DDG结果，并得出结论："start 是一个方法参数... 在 njs_string_offset 中没有对 start 的赋值；它是被直接传递的... 必须转向调用者。"

为什么这是错的： 这个结论是不正确的。start 变量在 njs_string_offset 函数内部被修改（污染）了。

正如我们在之前的对话中讨论过的（基于 GitHub 报告），njs_string_offset 函数中存在以下代码：

C

// ...
start += map[index / NJS_STRING_MAP_STRIDE - 1];  // [!] 'start' 在这里被修改
// ...
for (skip = index % NJS_STRING_MAP_STRIDE; skip != 0; skip--) {
    start = njs_utf8_next(start, end);                // [!] 污染过的 'start' 在这里被传递
}
迭代 4 中的DDG（数据依赖图）甚至找到了这个赋值点（List(2541), "start", "Identifier"），但分析师错误地忽略了它，只关注了 MethodParameterIn（方法传入参数） 这一事实。

3. 错误的方向 (迭代 6-21)
由于这个错误的结论，分析师执行了一个不必要的转向 (Pivot)。

错误路径： 迭代 6 到 21 都在追踪start指针的原始来源。它一路追溯 njs_string_prototype_last_index_of 和 njs_string_prop，最终发现该指针来自 value->short_string.start。

为什么这无关紧要： 崩溃不是因为 value->short_string.start 指针本身是无效的。崩溃是因为这个（最初有效的）指针在 njs_string_offset 内部被一个无效的偏移量（来自越界读取 map[...]）污染了。

4. 错误的结论 (迭代 24)
分析师最终得出的结论是，c = *p++（njs_utf8.h:52） 发生在一个循环的边界检查 p < end 之前。

虽然这个观察（p 在检查前被解引用）在技术上是正确的，但这并不是此 CVE 的根本原因。njs_utf8_next 函数假定它接收到的 p 是一个有效指针。

真正的漏洞（CVE-2022-38890）是 njs_string_offset 函数未能保证它传递给 njs_utf8_next 的 start 指针是有效的。

总结
正确的分析轨迹本应是：

停留在 njs_string_offset 中。

识别出 start += map[...] 是对 FOCUS 变量的本地修改。

将 FOCUS 切换到导致这个修改的变量上，即 map[index / ...]。

这将会揭露出 map 上的越界读取 (OOB Read)，而这才是该漏洞的真正根源。

因此，这个数据流分析的轨迹是错误的；它错误地转向，去追踪一个无关紧要的指针来源，而不是调查导致指针损坏的本地变量（即 index 和 map）。

偏差是如何发生的
1. 迭代 4：找到了关键线索（但未被理解）
Joern 的输出是正确的。它说 start 变量（在第 2545 行的 njs_utf8_next 调用中）的数据流依赖于：

(List(2529), "const u_char *start", "MethodParameterIn")

含义： start 的初始值来自函数（njs_string_offset）的同名输入参数。

(List(2541), "start", "Identifier")

含义： 在第 2541 行，start 变量被引用或被赋值。这是数据流路径上的一个关键节点。

(List(2545), "start", "Identifier")

含义： start 在第 2545 行被使用（这是我们查询的SINK点）。

List(2541) 就是那个“指向宝藏的X标记”。正确的下一步本应是调查第 2541 行到底对 start 做了什么。

2. 迭代 5：做出了错误的结论
这是分析开始出现偏差的地方。请看分析师在 intent（意图）中写的内容：

"S2 shows FOCUS=start is a method parameter ... and used as identifier at lines 2541 and 2545. No assignments to start within njs_string_offset; it is passed through directly. ... No local assignments found; must pivot to caller."

分析师犯了两个错误：

错误的假设： 它将第 2541 行的 Identifier 错误地解读为“只是一个使用（use）”，而不是“一个赋值（assignment）”。

过早的结论： 它过分关注 MethodParameterIn (来自第 2529 行) 这一事实，并立即得出结论：“哦，它只是一个被传递的参数”。

它看到了第 2541 行的线索，但选择忽略它，并错误地断言“没有本地赋值”。

3. 迭代 6：执行了错误的转向
基于迭代 5 中的错误结论，分析师在迭代 6 中执行了致命的错误操作：

"S5_PIVOT_GATE: S2/S3 confirm FOCUS=start is a parameter with no local assignments in njs_string_offset. Pivoting to caller..."

分析师现在完全离开了 njs_string_offset 这个**“犯罪现场”**（指针被污染的地方），转而去追踪指针的原始来源（在 njs_string_prototype_last_index_of 中）。

但我们知道，指针的原始来源是无辜的；它是一个有效的指针。真正的漏洞是它在 njs_string_offset 内部被一个无效的偏移量（来自 map[...] 的越界读取）所污染。

总结
偏差的发生是因为分析师（AI）在迭代 5 中对其在迭代 4 中收集到的数据做出了草率的、不正确的解释。

它本应： 调查第 2541 行的 start 标识符，看看它是否在赋值操作的左侧（例如 start = ... 或 start += ...）。

它实际做了： 错误地断言没有本地赋值，并转向了调用者，从而错过了真正的漏洞。
